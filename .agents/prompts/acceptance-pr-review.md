# 验收 PR 的 AI 复审提示词（自装审批第二步，2026-11-02）

> 用途：业主或流程把本文件连同 PR 号交给任意 agent（“按 `.agents/prompts/acceptance-pr-review.md` 审 PR #N”），
> 即产出设计稿 §5.5 规定的独立复核。**只读**：不改进工作区、不直接改结论、不合并。
> 触发范围：`accept/PKG-*` 分支的验收 PR（代码/文档 PR 不需要本流程）。

## 0. 输入

- PR 号（或分支名）。先 `gh pr view N --json title,body,baseRefName,headRefName,files` 与
  `gh pr diff N` 拿全貌；`gh pr checks N` 拿 CI 状态。

## 1. 能审什么（记录 vs 配置的一致性）

逐条过，每条都要落到 diff 里的文件和行号：

1. **PR 描述逐条 claim 对 diff**：描述说改了哪些检查/证据/文件，diff 里是否确实是这些；
   没改的是否真没改。对不上即 P0。
2. **headline 数字独立重算**：不引用描述里的数。用机器源重算——
   `npm run verify:schedule`（包/检查/未报价/门禁阻塞数）、`npm run takeoff:ceiling`、
   `npm run verify:facts`（对账结论）。描述数字与机器数不一致即 P0。
3. **生成物与生成器一致**：diff 里若有 `schedule/**/*.md`（渲染产物），确认
   `npm run schedule:render` 后无漂移（`git diff -- schedule/` 为空）；指纹快照注释与输入一致。
4. **audit 记录合规**（验收 PR 核心）：逐条新记录查——`check_spec_sha256` /
   `project_data_sha256` 与当前 loader 计算值一致（否则提交即 stale）；
   `supersedes` 指向更早记录；passed 必有 evidence 且文件在 diff 里真实存在；
   被 open 决策门禁阻塞的检查无 passed 记录。
5. **门禁与基线**：CI 四任务对照 `ci/baseline/`——只允许“基线内失败”，出现基线外新失败即 P0；
   基线行只删不增（删了必须在 PR 描述里说明是哪条、为什么）。
6. **最危险的一条单独探**：找出本次改动里“错了会让业主付错钱/返工不可逆”的那一条
   （通常是金额、指纹、依赖、付款门槛），单独深挖到底。

## 2. 不能审什么（只提醒人核，不签章）

- 照片是不是今天拍的、拍的是不是这面墙、箱唛是不是合同里那个批次、尺寸是不是现场量的——
  **这些 AI 一律判不了**。若 PR 描述把它们当作既成事实，指出“此条未经人核，合并前请业主现场核对”。
- 不要把“记录自洽”表述为“施工合格”。

## 3. 输出格式（verdict 必须落仓）

结论发 **PR 评论**（`gh pr comment N --body ...`），不只活在对话里：

```
## AI 复审结论

**逐条核对**：<claim → diff 证据（文件:行）→ 符合/不符>
**数字重算**：<描述数 vs 机器源数 → 一致/不一致>
**audit 合规**：<逐条记录的指纹/supersedes/evidence/门禁检查结果>
**最危险单项**：<深挖结果>

**分级**：P0 <n> 条（<一句话列表>）｜P1 <n> 条｜P2 <n> 条
**合并结论**：能合 / 修完再合 / 不能合
**待业主现场人核**：<照片/尺寸/批次类条目，没有则写“无”>
```

- P0 = 拦合并（记录与 diff 不符、数字造假、基线外新失败、指纹不符、门禁被绕过）
- P1 = 合并前修（缺说明、缺测试、文案与实现不一致）
- P2 = 以后修（不影响本次正确性）
- 合并永远由业主亲手点；本流程只到评论为止。

## 4. 历史教训（必读，都是真挨过的）

- **不许静默取首个**：多候选（多 link、多包）时必须全部列出或显式说明取舍。
- **测试数写实算数**：PR 正文的测试条数必须逐文件数过，不许估算。
- **截图/证据描述=实情**：没拍到的场景不许写“已走通”；工具做不到的（如 1.2s 闪现）
  如实登记为未验证。
- **配色之外必须有文字**：状态色不作单独证据。
- **diff 出删了什么**：PR 若删除了具体候选/证据/基线行，必须逐条说明理由。
