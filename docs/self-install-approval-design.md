## 0. 起点：为什么要这套东西

小红书帖子里的问题不是某道工序错了，而是口头安排加信任透支：业主问顺序、下一步、能不能写成文字，工长理解为不信任，拒绝书面说明，最后情绪先于技术升级。
自装没有工长，这个角色并没有消失，是转移到业主身上。没有一张强制走的图和一张能点的审批流，口头节奏和工长的"信我"其实是一回事。
本设计要把"问清楚、写下来、凭证据、按节点付"变成一个不靠临场发挥的交互，而不是靠每次聊天重新想一遍。

这不是新发明的仪式。本项目已经在 config 上跑 CI：typecheck / test-server / test-app / verify-all 四任务加基线对照，其中 verify-all 已包含 verify-schedule 与 verify-decision-gates 两步——依赖、指纹、契约、视图漂移今天就是机器判的。自装交互审批 = 把同一条纪律从 config 推到现场。

## 1. 设计总览（一句话）

以系统配置为唯一事实源的**施工 CI**：CI 的测试用例在现场（照片、尺寸、闭水 48 小时），CI 的发布动作是付款（合并即放行付款节点）。
和 3D 模型共一个 web 站点（浏览器打开，不做原生 app），用流程图和门禁图管理进度，包和检查项全部可视化，点流程节点能跳到 3D 看状态，点 3D 对象能反向回到包和检查，每包走"现场验收 → 机械卡点 → 提交 PR → AI 审核 → 业主亲手合并"这一条闭环。

3D 管是什么、在哪；流程图和门禁图管做到哪、过没过；next-action 管现在干什么。两边不互相定义对方。

首屏默认 next-action（下一个动作），不是全局红图——业主打开来第一眼必须看到"今天能干什么"，而不是 25 个 blocked。

## 2. 不可动摇的原则

- 没证据判 pending，不判 passed；口头说完工不算完工。证据不进仓，验收视图就是空的——接受"空"，不靠印象补。
- 验收没过不给钱；付款只绑验收节点，不按进度百分比付。
- 配置是权威源，清单是配置的投影；配置一变，旧 PASS 自动转 stale，回到 pending。（`check_spec_sha256` / `project_data_sha256` 就是缓存失效键，和源码变了测试作废同一个机制。）
- 决策门禁没拍板，被它阻塞的检查不得判 passed，付款自然 pending；决策一个一个拍，不批量代定。
- 助手不合并，合并一律业主亲手点；现场验收、PR 作者、合并人即使是同一个人，也必须是三次分开的点击，不能一键直通。
- **AI 的合并结论是记账校对，不是质检签字。** 它只校对"记录与配置一致"：叙述对得上 diff、headline 数字独立重算、指纹与契约合规、生成视图已同步。照片真伪、现场真伪、箱唛批次永远人核，AI 只逐条提醒，不签章。
- **现场快、仓库慢。** 现场 30 秒内完成"拍照→挂到当前检查项→看到 pending/passed"；PR 是每包一次的异步提交步。不许把现场节奏绑在 PR 上，那是绕过系统的第一入口。
- 不设第二套账：交互状态必须写回同一套清单和审计记录，不能另起数据库或只存在浏览器里。

## 3. 架构：三层，共享一个选中 ID

数据层（唯一事实源，不复制）：
- 几何与结构：config/layout/model-geometry.yaml、overlay.yaml
- 验收标准本体：config/acceptance.yaml（各阶段只引用 ID，不复制第二套标准）
- 一期控制源：schedule/phase-1/control.yaml、schedule/phase-1/checklist.md（自动生成视图，只读投影）
- 决策门禁：config/decision-gates.yaml、D1-D18 登记
- 包与模型关联：config/model-package-links.yaml（只做关联索引，不复制金额、坐标、证据；facts.yaml coverage 三字段**已补登记，PR #48**，改它有门禁看）
- 审计与合同：control.yaml 的 audit_log、contracts/ 原件加登记块（金额、成交状态、签约日期、含不含范围、archive_paths）

**共享 loader 约束（硬性）**：scripts/schedule/control.ts 有模块级副作用（`renderMode` 在顶层，文件尾直接跑检测、console.log、设 exitCode），server 和前端不得直接 import 它。第一步先抽无副作用 loader（拆分 control.ts 或新建共享 loader 模块——实际落点 shared/schedule-state.ts），CLI、CI、新 API 三者共用同一个 loader——判定规则从此只有一处，见 §5.3。

视图层（同一站点，面板共用选中 ID）：
- 首屏：next-action 视图（见 §7）
- 左：进度图（一期包链）＋门禁图（CI 与决策门禁，分开两个模式，不合成一张）
- 中：3D 模型
- 右：详情面板（包、检查、证据、物料、阻塞、门禁、付款节点、审计历史）
- 选中状态可进链接地址，方便直接发某个包或某面墙的链接

写路径层（见 §5 节）：机械卡点 → PR → AI 审核 → 业主合并。
写边界（与既有机制划清，防止误伤）：
- **走 PR 的写**：audit_log 记录、门禁拍板（D* decided 四件套）、包/检查状态、paid_cny 回写
- **维持现有浏览器直写的**：设计配置编辑（furnishings / electrical / plumbing 走既有 editYaml 路由）——不搬进 PR 流，本设计不改变它

## 4. 状态模型

包状态：not_started、in_progress、ready_for_inspection、passed、failed、blocked、waived（豁免须批准人、理由、证据）。词表与 control.yaml `status_values` 逐字一致。
检查状态：pending、passed、failed、not_applicable；复验追加新记录，用 supersedes 指旧记录，不覆盖历史。
包通过条件：全部检查当前通过、数据指纹未过期、依赖和阻塞仍满足，由 `npm run verify:schedule` 判定并报错，清单按 blocked/stale 展示——**判定只有这一处**。

物料状态（三档是**归组投影**，不是新词表——control.yaml 现有 60+ 种 status，新造词表就是第二套账，直接撞 facts.yaml 的 parity 契约）：
- 候选（在选）：quote_pending / selection_pending / candidate / candidate_pending_quote / pending_quote / owner_decision_pending / budget_pool_confirmed_quote_pending 等未定价未锁定族
- 锁定：locked（facts.yaml requires 契约已强制 locked_cny + contract_ref + evidence_path 三字段；contracts/ 的合同登记块 + archive_paths 指向原件即在位证据。文件哈希机制暂不引入——要做必须读者、校验器、facts 登记三件套齐全，否则维持"登记块+原件在位"口径）
- **到场不是物料状态字段，是证据事件**：落在检查的 evidence_required 与 audit record（送货单、箱唛同批照片、现场照片、测试记录）。理由：仓库的证据声明挂在检查上，物料条目没有"到场"字段，硬加就是双写

门禁状态：CI 四任务（typecheck、test-server、test-app、verify-all）只判基线外新失败；决策门禁 open 即阻塞。

当前真实状态（2026-11-02 实测 `npm run verify:schedule`）：25 个包全部 not_started / blocked（0 个 ready）、audit_log 空、付款 25 个门禁无一放行；116 项可审计检查；106 个成本组件中 89 个无价；7 条 open 决策门禁阻塞 13 项检查；已分配 ¥210,000，已知缺口 ¥36,385。状态图画出来以待做和被阻塞为主，这是对的，不是图没做好。

交房前可做的可逆预演要标 can_run_while_blocked 且 does_not_release_construction，通过它不解除施工 readiness。

## 5. 交互流程：每包同一条闭环

> **caveat（2026-11-03 #51 合入后复核结论）**：本节写路径部分与 PR #51 实现逐条比对一致——五道机械卡点（控制源/草稿/证据在位/前置与阻塞/verify:schedule 当前树）与 §5.3 判定清单对齐；PR 正文由 `shared/acceptance-draft.ts` 的 `renderPrBody` 从草稿生成（§5.4 已据此更正措辞）；AI verdict 落仓由 `.agents/prompts/acceptance-pr-review.md`（PR #55）承载。v2 新增内容自此可称定稿；试点包 PKG-060 尚未实跑，§11 第二步的成败判据仍待首包验证。

```
点进去 -> 做验收 -> 机械卡点 -> 提交 PR -> AI 审核 -> 业主合并 -> 下一包解锁
   ^        失败/补证据        |  P0/P1            |
   +------ 整改、重新验收 ------+---- 追加提交、重新审核
```

1. 点进去
   点包展开检查项，每项显示方法、通过标准、必需证据类型、关联物料卡片、阻塞项和决策门禁。
   开工前先发确认单：范围、顺序、验收点、证据、付款节点。对方拒绝书面确认、拒绝拍照留证、拒绝按节点验收付款，合作前换人。
   **这是整套架构的单点故障防线**：证据进不了仓，上面的 PR、AI、门禁全部空转。它不是流程里的一句劝退，是地基。

2. 做验收（业主在现场）
   拍照、量尺寸、留测试记录和单据，按包归档，附到对应检查项上。无证据的项判 pending。
   要改顺序先改确认单、业主点头，不按师傅口头改。
   现场动作必须 30 秒内完成：拍照→自动挂到当前检查项→当场看到 pending/passed。采集是现场的事，提交是桌面的事，两者不许互相等待。
   证据归档接证据分级铁律：过程版照片、转储文件进 tmp/capture/ 不进 git；进仓的只有终稿（每视角至多 1 张）与外部原件（合同、报价、厂家资料、业主提供图），外部原件在该轮 brief 登记来源。

3. 机械卡点（机器判，不讲道理——判定单一实现）
   **全部判定由 `npm run verify:schedule`（scripts/schedule/control.ts）执行，CI 的 verify-all 已含 verify-schedule 与 verify-decision-gates 两步。** 交互层只通过同一 loader 读取结果并指名是哪道卡点、怎么补，**不得在浏览器里复述任何判定规则**——UI 里第二套卡点逻辑，就是 verify:schedule 改规则时 UI 不跟随、两边结论互相矛盾的入口。
   判定清单（现状已实现，UI 只呈现）：证据文件存在且打得开；检查指纹和项目数据指纹是当前的；决策门禁没阻塞；前置包已 passed；复验 supersedes 指向更早记录；必填字段（checked_by、checked_at、证据路径）齐全；生成视图已重渲。
   有一项不过就不让提交，界面指名是哪道卡点、怎么补。提交后 CI 再跑远程机械卡点，基线外新失败才判红。

4. 提交 PR
   一个包一次 PR，不要一个检查一个 PR。
   **PR 描述由脚本生成，不手写**：`shared/acceptance-draft.ts` 的 `renderPrBody` 从草稿派生改了哪些检查、没改哪些、新增证据清单、指纹、放行哪个付款节点（2026-11-03 复核更正：原写「直接贴 `schedule:audit` 输出」，实际生成器是 renderPrBody，schedule:audit 是另一条 CLI 输出）。业主只改措辞。手写描述是绕过的第一入口，生成式描述把它堵了。

5. AI 审核（只读远端 diff，不改工作区，不直接改结论）
   描述里的每条 claim 都拿 diff 里的文件和行号去对；headline 数字自己重算（可调 takeoff / verify:facts 机器源，不是猜）；生成文件和生成器、指纹对不对得上；最危险的一条单独探一下。
   **职责边界写死**：
   - 能判：叙述与 diff 逐条一致；数字独立重算；supersedes 链与指纹合规；生成视图已同步；门禁四件套齐全；有没有造第二套账
   - 不能判：照片是不是今天拍的、拍的是不是这面墙、箱唛是不是合同里那个批次——这三项 AI 只逐条提醒人核，结论不得表述为质检通过
   结论分 P0 拦合并、P1 合并前修、P2 以后修，最后给合并结论：能合、修完再合、不能合。
   **AI verdict 必须落仓**（写进 PR 记录或 audit 附属字段），不活在聊天里——否则"AI 审过"本身没有审计痕迹。
   机械卡点看不出来的东西靠这一层提醒，例如照片是不是真的拍到了倒水流向地漏、量出来的尺寸跟几何对不对得上、箱唛是不是合同里那个批次——注意这三项是**提醒人去核**，不是 AI 代核。

6. 业主亲手合并
   AI 说能合才合；有 P0/P1 就回去整改或补证据，在同一 PR 里追加提交，重新跑机械卡点和 AI 复核。
   合并后 master 里的状态才算 passed，下一包才解锁，付款节点才算放行。
   付款节点放行动作里绑定 paid_cny 回写，一步完成——不让"已付"只活在业主脑子里，那是系统察觉不到的漂移。
   现场验收、PR 作者、合并人即使是同一个人，也必须是三次分开的点击，不能一键直通。

- 没有几何的包（物业手续、竣工结算、合同类）点它跳文档和清单面板，明确标成全项目范围，不硬找个 3D 位置。

## 7. next-action 视图（v2 新增，全案最缺的一块）

为什么：进度图和门禁图回答"有哪些、过没过"，不回答"**现在干什么**"。没有这个视图，业主打开来面对 25 个 blocked 的包仍然不知道今天该干嘛——系统就只是个更漂亮的病历，不是导航。它也是红图疲劳的解药：默认首页永远是"今天能推动的一两件事"，不是全局红图。

算什么（三条线索交汇，全部来自既有数据，无新数据层）：
1. **就绪的包**：依赖全 passed 且阻塞已关闭 → readiness ready 的，今天能开工或能验收
2. **待拍板的门禁**：open 决策门禁阻塞的检查（当前 7 条阻塞 13 项），每条带 options 与 decided 四件套要求
3. **待询价的物料**：未定价成本组件（当前 89/106），按包聚合
4. **系统外动作单列**：燃气门、物业手续、量房这类系统推不动的，只标记"等外部方"，不混进"等业主自己"——否则业主会把视图当完整真相，漏掉只有打电话能推进的事

排序按"解除最多下游"优先（依赖拓扑深度）。与进度图的关系：进度图看全局，next-action 是首页。

## 8. 证据与物料的详情面板长什么样

点一个检查项，右侧同时出现：
- 方法、通过标准、级别
- 必需证据类型和已上传的证据文件（照片、检测记录、视频截图、单据），每个文件能打开
- 关联物料卡片：候选、锁定、到场三档分开（映射见 §4），锁定须有合同引用，到场须有送货和同批证据
- 阻塞项、决策门禁、付款节点
- 审计历史：历次记录、复验 supersedes 关系、指纹是否过期

**交互表单由清单生成，不是每项手写；证据字段的唯一权威是 control.yaml checks 的 `evidence_required`**——audit 记录挂在 control.yaml 的 check_id 上；acceptance.yaml 里的 evidence 是标准侧参考，不作表单权威，否则生成器读哪份是随机决定。

例如 PKG-060：空鼓（`check_tile_hollow`：单片空鼓率 <15%、整面墙 <5%）、坡度（`check_tile_slope`：倒水流向地漏、不积水）、贴砖当天倒水（`check_tile_slope_same_day`：半盆水 10 秒内全部流向地漏，当天返工重找坡，不得等美缝）、防水台面砖（`check_sill_tile`：逐窗核对竖面和台面）——每项的必需证据类型都不一样，表单由上述权威字段生成。

## 10. 不做什么

> **caveat（2026-11-03 #51 合入后复核）**：本节「不直接写 master、不绕过 PR、不让浏览器持有写仓库的令牌」与 PR #51 实现一致（accept/ 分支 + commit + push + gh pr create，合并仍在 GitHub 由业主点）；写路径措辞自此为定稿。

- 不做公司式 OA：多级审批、角色权限、通知流、BPMN 引擎、独立数据库、公网部署——除非用户重新拍板部署口径。
- 不直接写 master、不绕过 PR、不让浏览器持有写仓库的令牌、不让师傅进系统自批。**边界**：验收状态、audit_log、门禁拍板、paid_cny 走 PR；设计配置编辑（家具/水电点位移来移去）维持现有浏览器直写路由，本设计不改变它。
- 不把浏览器本地状态当事实源；不把候选价当成交价；不把设计模型当成已施工事实。
- 不把流程图和门禁图合成一张；不把颜色当证据；不为了凑链接凭空发明 3D 类型；不在交互层复述机械卡点判定规则。
